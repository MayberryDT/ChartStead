01 / Research

What the research actually found

The starting point was not a desire to add more confirmation dialogs. It was repeated evidence that organizers must manually reconstruct the consequences of decisions that span several systems.

02 / Problem

The danger lives between modules

A normal confirmation modal sees the button being pressed. The operator's real decision crosses review state, identity, communication, scheduling, public output, and integration state.

Committee decisionApprove a proposal internally.Can change repeatedly
Record creationCreate speakers, participation history, sessions, and onboarding tasks.Duplicates possible
Recipient assemblyResolve people, co-speakers, addresses, exclusions, and previous contact.Manual checking
Program changePlace or publish sessions while conflicts and TBD states remain.Partial truth
External effectsSend email, update calendars, publish pages, and synchronize Airtable.Not truly undoable

The researched problem: no single module can answer the operator's full question. Each module may be correct locally while the combined action is wrong globally.

03 / Reasoning

How we got from pain to the proposed boundary

The design deliberately rejects both extremes: one narrow confirmation screen is not differentiated enough, while a universal workflow engine would generalize before ChartStead understands enough workflows.

Design questionHow can ChartStead make consequential actions inspectable without turning every edit into ceremony?
Rejected

Focused confirmation screens

Fast to build, but each workflow invents its own stale checks, retry behavior, audit, and vocabulary. Safety semantics drift.

Selected

Shared safety kernel

One versioning, approval, execution, and recovery contract. Three specialized planners retain the real domain rules.

Rejected for now

Universal workflow engine

Maximum abstraction, but it creates a generic effect language, plugin system, and graph executor before they are justified.

01

Batch proposal decisions

Internal decisions, acceptance cascade, created records, tasks, and integration effects.

02

Speaker communication

Exact recipients, exclusions, prior contact, drafts, email, and calendar delivery.

03

Program publication

Public schedule delta, unresolved private work, calendar changes, and external writes.

04 / Solution

One safety contract, proportional ceremony

The kernel is always active for the three selected actions. The visible review expands only when the consequences need attention.

Always-on machineryPlan versioning, freshness checks, authorization, idempotency, transactional writes, effect records, retries, and audit.
+
Proportional reviewClean reversible work stays concise. Warnings, exclusions, stale inputs, public changes, and irreversible effects expand.
Apply decisionsChange internal state and create required records.
Create draftsPrepare editable communication without sending.
Send and deliverEmail and calendar effects leave ChartStead.
Publish programAttendee-facing state becomes public.
Write integrationsAirtable and other systems receive changes.

Important distinction: five approval boundaries do not require five pages. A single review surface can show all stages while recording exactly which stages the operator approved.

06 / Architecture

How the safety kernel works

The kernel is a deep module inside the event's Durable Object. UI and API callers use the same interface; domain-specific planners prepare the evidence; one transaction commits internal truth and queues external work.

Safety kernelShared lifecycle
  • Plan versions freeze the exact reviewed intent.
  • Targeted revision checks detect changed relevant inputs.
  • Approval hashes bind approval to one immutable plan.
  • Stage policy preserves the five consequence boundaries.
  • Idempotency makes repeated requests return the same result.
  • Effect ledger tracks every external outcome independently.
  • Audit history records request, review, execution, failure, and correction.

One local transaction - all four commit or all four roll back
1. Recheck inputsCompare only relevant entity revisions and current authorization.
2. Apply internal stateWrite decisions, records, snapshots, or publication pointers.
3. Create effect rowsFreeze one independently trackable outbox effect per recipient or external write.
4. Append auditRecord the exact actor, plan, stage, digest, and resulting state.

Why network calls are outside the transaction: email, calendar, and Airtable cannot join a SQLite transaction. The transaction records the durable intent first; an alarm-driven dispatcher then executes each effect idempotently.

07 / Policy

What "mandatory kernel, proportional review" means

The product never creates a weaker alternate mutation path. It does vary how much attention the interface demands based on consequence and uncertainty.

Situation
What the kernel does
What the operator sees
Ordinary low-risk editEdit a biography or internal note.
Normal domain writeOutside the visible safety flow; still authorized and audited where required.
No extra ceremonyThe user saves normally.
Clean consequential planNo warning, exclusion, stale input, or failed effect.
Full safety lifecycleVersions, checks, approval, transaction, outbox, and audit still run.
Concise reviewLow-risk detail collapses. Required external approvals remain explicit.
Risk or uncertainty foundMissing contact, prior send, conflict, stale data, or unavailable integration.
Block or isolate preciselyStale plans block. Soft warnings remain overridable. Effects stay independent.
Expanded evidenceThe affected people, records, warnings, and choices become prominent.

No global off switch: disabling only the screen while retaining the kernel would create invisible automation. Disabling both would create a second, unsafe write path. Proportional review removes friction without removing trustworthy semantics.

08 / Failure

How failure stays truthful

The system never reports a batch as simply "done" when some effects are still pending, failed, or unknowable.

Input changed before approvalA speaker address, decision, schedule, template, or permission changed.
Provider returned failureEmail, calendar, publication, or Airtable rejected the request.
Outcome is ambiguousThe provider may have accepted the effect before the connection failed.
→
Stale planBlock application, identify the changed inputs, and generate a new plan version.
Per-effect failureKeep successful effects terminal and retry only safe failed effects.
Unknown stateStop automatic retry until the outcome can be reconciled.
→
Review againApprovals never transfer automatically to a changed plan.
Resume safelyIdempotency prevents repeating internal work or completed effects.
Compensate forwardCreate a new reviewed correction, cancellation, restoration, or corrective sync. Never claim email was unsent.

Decision in front of us

Keep the safety kernel mandatory. Make the review ceremony proportional.

This preserves one trustworthy execution path while keeping the organizer experience concise when nothing needs attention.

1Only the three selected consequential workflows use the visible safety layer in the first release.
2Clean and reversible detail collapses; warnings and irreversible effects expand.
3Send, publish, calendar delivery, and integration writes always retain explicit approval.
4No alternate direct path bypasses freshness, idempotency, effect tracking, or audit.

09 / Precedents

Yes, parts of this have been done before

No single open-source project is the complete model. The proposed design combines mature patterns from source control, infrastructure planning, server-side admission, conference operations, outboxes, and durable workflows.

Where it resembles GitGit builds a candidate snapshot, lets someone inspect a delta, and records exactly what was committed. ChartStead also needs a frozen candidate, a focused diff, and an immutable record of the approved result.
≠
Where Git is not the modelA Git commit does not email people, update calendars, publish an attendee schedule, or write Airtable. Git can bypass hooks and some staging flows. ChartStead cannot permit a second path around the authoritative kernel.

10 / Staff reality

Five ways this helps conference staff without getting in the way

The key rule is simple: entering and correcting private truth stays immediate. Review appears when the next click tells people, changes the public program, or fans one decision into many records.

1
Fix a speaker detail while they are on the phoneAn AI Engineer staff member corrects a job title, biography, headshot, or dietary note shortly before doors open.
→
Immediate saveNo plan page and no generic confirmationThe kernel authorizes, validates, checks the record revision, saves, and audits in one request. Incomplete information and soft warnings do not block the correction.
→
BenefitThe staff member gets the person through quickly without sacrificing data integrity or losing who changed what.
2
Add a last-minute sponsor sessionA guaranteed speaker arrives late and staff create the speaker, private session, and a TBD room before the conference starts.
→
Immediate private workSave the truthful incomplete stateThe session can remain unplaced or conflicted. Focused review appears only when staff publish it or send a calendar invitation.
→
BenefitChartStead does not demand fake completeness, but it prevents an unfinished private session from becoming public by accident.
3
Move a room after attendees have arrivedA room becomes unavailable. A producer moves one session in the private schedule and leaves another session temporarily conflicted.
→
Focused release reviewThe move saves immediately; publication is separateBefore release, staff see the attendee-facing delta, affected embeds, two calendar updates, and the unresolved private conflict. They can publish the valid change without sending speaker messages yet.
→
BenefitThe public program changes deliberately while the internal schedule can remain honestly messy during the emergency.
4
Retry one failed acceptance emailA batch of 120 decision messages succeeds for 119 recipients; one address temporarily rejects delivery.
→
Effect recoveryRetry only the failed effectThe execution receipt preserves the 119 successes, shows the provider failure, and retries the same frozen message with the same idempotency identity.
→
BenefitStaff do not resend the whole batch, duplicate messages, or reconstruct delivery state from the provider dashboard.
5
Apply committee decisions after a long review meetingStaff select 30 proposals to accept and expect speakers, sessions, tasks, drafts, and Airtable records to follow.
→
Focused decision reviewCatch the expensive mistakes before the cascadeThe plan exposes a duplicate speaker identity, one missing co-speaker address, two prior acceptance sends, and three accepted sessions that remain safely unplaced. Internal decisions can apply without sending anything.
→
BenefitThe system replaces manual spreadsheet and inbox checks exactly where one mistake would multiply across records and people.

What must never block quick staff work

  • Typos, biography edits, headshot replacement, and internal notes
  • Recording approve, maybe, or deny during committee deliberation
  • Drafting or editing an unsent message
  • Moving sessions in the private working schedule
  • Saving TBD, unplaced, incomplete, or softly conflicted truth

What can legitimately stop a consequential apply

  • The staff member lacks permission
  • A relevant record changed after review
  • Identity ambiguity could create duplicate people or sessions
  • An external effect cannot be previewed safely
  • A hard invariant would corrupt durable state
